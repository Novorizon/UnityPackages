# 连续组件存储规划（第 5 项，尚未实现）

本文规划在第 1～4 项完成之后的存储重构，不声明当前框架已经具备以下 API、连续数据布局、世界隔离或并行查询能力。示例中的 `DataWorld`、`EntityHandle`、`IDataComponent`、查询和调度接口均为拟议接口。

[移除 MVC 依赖](MVC-DECOUPLING.zh-CN.md)独立于本规划：先以显式 Runtime 承接当前实体表、执行组与事务，保持 class 存储和 World 共享实体语义；不把该拆分误称为已经完成本规划的世界所有权、Sparse Set 或 Chunk。

当前审计基线见 [改进说明](OPTIMIZATION.zh-CN.md) 和 [性能方法](../Tests~/PERFORMANCE-BEFORE.md)。本次第 1～4 项保留托管 class 组件，以唯一类型 ID、成员索引、swap-remove、结构变更缓冲和按依赖通知改进现有框架。完成这轮修改后，应以新的基准作为本规划的性能对照；不使用审计前的 O(N²) 开销来夸大后续存储收益。

## 建议路线

先建立实体身份和世界所有权，再为选定的数值组件增加 **Sparse Set** 存储。保留 class 组件兼容层，让一个真实业务系统完成迁移和测量；只在查询占主导、组件组合稳定的场景证明有必要后，再引入 **Archetype Chunk**。

这不是一次全量重写。Sparse Set 和 Chunk 可以共享句柄、类型注册、命令缓冲及查询语义，但底层布局和多组件查询实现不同，不能承诺直接替换一个容器即可完成演进。

| 场景 | 优先选择 | 原因与代价 |
| --- | --- | --- |
| 组件组合变化频繁、组件类型较多，单组件或少数组件查询较多 | Sparse Set | 单类型数据连续，增删通常只改对应池；多组件查询仍需交集查找，访问其它组件列可能不连续。 |
| 少量固定组件组合，大量实体反复执行相同多组件计算 | Archetype Chunk 候选 | 同组合的多列按行对应，可批量扫描；加减组件会迁移行，组合过多会产生小块和碎片。 |
| 包含 UnityEngine.Object、字符串、容器、委托或业务对象引用的组件 | 托管兼容池 | 保留 class 语义；连续的是引用或索引，不是对象字段，不能当作 Burst 可用的连续数值数据。 |

## 1. 实体身份与世界所有权先行

拟议值类型句柄包含 `WorldId + Index + Generation`，不把可复用的 `Entity` 对象引用作为身份。`Index` 指向该世界的实体槽位，回收后增加代际；访问前必须同时校验所属世界、存活状态和代际。

```csharp
// 拟议的数据形状，非已实现 API。
public readonly struct EntityHandle
{
    public readonly ulong WorldId;
    public readonly int Index;
    public readonly uint Generation;
}
```

- 每个 `DataWorld` 拥有实体槽位表、空闲槽位栈、各类型组件池、命令缓冲及查询缓存。世界 A 的句柄不能用于世界 B；运行期 WorldId 不重复分配。
- 槽位表保存当前 generation 和 alive。销毁提交时使旧句柄失效，再把槽位放回空闲表；代际溢出时退休该槽位，不能静默绕回而重新接受很旧的句柄。
- 当前 `ECS.World` 实际是系统执行组。引入 `DataWorld` 时应显式区分“拥有实体的世界”与“在某个世界上执行的系统组”，不静默改变旧多 World 广播行为。
- 现有静态 `EntityManager` 可以作为默认 DataWorld 的兼容门面。旧 `Entity` class 包装句柄和业务 GUID，继续服务 GameObject 及已有业务代码；新代码优先使用值句柄。
- GUID 可继续作为日志、存档或网络业务标识，但运行期槽位身份与持久化标识分开。运行期 Type ID 和 WorldId 均不直接写入持久格式；存档/网络协议使用有版本的稳定类型标识并校验映射。

这一阶段先在测试中确定旧 API 与新句柄的映射规则，尤其是对象池复用、异步请求、默认世界和多个系统组，之后才移动组件数据。

## 2. 托管与数值组件采用两条明确路径

保留当前 `class : IComponent` 及对象池 API。新增独立标记 `IDataComponent`，只允许 `where T : unmanaged, IDataComponent` 的数值结构体进入连续数据存储；不放宽旧 `IComponent` 的 class 约束来再次引入按值修改丢失的问题。

| 路径 | 存储与访问 | 适用范围 |
| --- | --- | --- |
| 兼容路径 | 现有 class 对象、类型 ID、系统成员索引；组件按引用修改 | GameObject、资源、UI、事件、业务对象及渐进迁移。 |
| 数值路径 | 每类型连续 `T` 数据列，显式 ref 写访问及只读访问 | Position/Velocity、计时、生命值、轻量状态等纯数据。 |
| 两条路径的桥接 | 句柄到托管表现对象的表，限定阶段同步 | 主线程把数值结果应用到 Transform；不把 GameObject 引用传入 Burst Job。 |

一个逻辑字段只能有一个权威存储位置。例如迁移 Position 后，原 Position class 应成为显式访问适配器或停用，不允许 class.Value 与 PositionData.Value 各自更新再尝试隐式合并。跨路径同步必须定义方向和执行阶段。

第一阶段可以使用托管数组验证布局和 API；它本身不意味着支持 Burst。进入 Unity Jobs 阶段后，再增加经过版本验证的原生容器后端，并声明、锁定与 Unity 2022.3 兼容的 Collections/Jobs 依赖版本。

## 3. Sparse Set 试点的数据结构与查询

每个 `ComponentPool<T>` 拥有三部分：

```text
denseEntities[row]  = 对应实体句柄
denseValues[row]    = T 的实际字段数据
sparse[entitySlot]  = row，缺失为 -1
```

先校验世界和 generation，再通过 sparse 找 row，并核对 denseEntities[row]。新增追加到 dense 列；删除时将末行交换到目标行，同步修正被移动实体的 sparse，最后移除末行。所有列必须一起移动；遍历顺序不稳定。

单组件遍历直接扫描 denseValues。多组件查询从最小的必需组件池驱动，对其它池做 O(1) 成员查找后取得各自的 row。它不会自动令 Position 和 Velocity 的同一实体位于相同行，不能直接把两列当成对齐数组一起扫描。

首版不默认缓存每个查询的完整实体集合；缓存组件池引用与查询计划即可。若后续测量证明交集查找占主要成本，再为热点查询加入成员缓存及增量维护，并把缓存维护开销纳入结构变更基准。

稀疏索引按世界槽位上限分配时，内存可能接近“组件类型数 × 槽位上限”。必须测量高水位、稀有组件和大量删除后的内存；只有出现实际浪费后再增加分页 sparse 或收缩策略。不能只报告 dense 数组的大小。

## 4. 拟议查询、ref 访问与提交规则

以下代码仅表达使用意图，具体类型和方法仍需在试点中确定；不是本次可编译的示例。

```csharp
// 拟议 API。
var world = new DataWorld();
EntityHandle entity = world.Create();
world.Data.Add(entity, new PositionData());
world.Data.Add(entity, new VelocityData());

var moving = world.Query<PositionData, VelocityData>();
moving.Run(new MoveStep(deltaTime));
// MoveStep.Execute(ref PositionData position, in VelocityData velocity)

world.Commands.Remove<VelocityData>(entity);
world.Playback(); // 在约定的安全边界生效。
```

查询执行期间取得的 ref/只读视图只在该查询作用域内有效。不能把 ref、row、数组视图或指针跨越 Playback、容量扩张、世界销毁或后续结构变更保留；swap-remove 也会改变 row 对应的实体。

开发模式用结构版本和借用计数检查非法变更。生产热路径是否保留检查应由配置决定，但不能靠调用方“通常不会扩容”保证引用安全。公开的单组件 `GetRef<T>` 若保留，必须返回带作用域的借用或强制相同的结构冻结规则。

同一帧的命令按明确顺序提交，销毁后的旧代际命令拒绝或作为已失效操作跳过。增加与移除相抵的命令可以优化，但不能改变中间可观察的回调、组件初始化/回收语义；先定义语义再做合并。多个同类型命令的保留值、重复 Add 的行为及异常处理都要有测试。

## 5. Jobs 与调度在单线程存储稳定后加入

拟议调度声明组件读写集合，例如移动系统“读 VelocityData、写 PositionData”。有写冲突的任务通过依赖串行化；纯只读任务才可共享访问。结构变更只由主线程在相关任务完成后 Playback，不允许 Job 直接访问托管字典、ReferencePool 或 GameObject。

```csharp
// 后续原生存储阶段的拟议 API，尚未实现。
var handle = moving.Schedule(new MoveJob(deltaTime), dependency);
handle.Complete();
world.Playback();
```

Sparse Set 多组件查询若各列 row 不一致，不能未经设计就按相同索引并行访问。可先把最小池分区，每行用只读 sparse 查找其它列；写入目标实体唯一时才允许该并行策略，并验证容器安全限制。任何临时索引表、重排或查询缓存的构建都要单独计时。

Unity 2022.3、IL2CPP 和 Burst 的泛型/AOT 支持需要真实 Player 验证。首版优先显式注册使用的组件与 Job，检查代码裁剪和泛型实例化；不要仅依靠运行时反射生成查询。安全句柄、任务异常、世界退出和容器释放必须覆盖实际 Unity 测试。

## 6. 何时进入 Archetype Chunk

进入该阶段之前，先用代表性系统证明 Sparse Set 的多池交集查找、数据局部性或查询缓存维护是实际瓶颈，并验证同类型实体的组件组合足够稳定。没有证据时保持 Sparse Set 实现。

Chunk 方案需要新增：

- 规范化的组件类型集合和集合相等判断；哈希只做加速，不能作为组合唯一身份。
- Archetype 内分块的同长度组件列，以及实体位置 `archetype/chunk/row`。块大小由组件实际大小、对齐、占用率和测试确定，不先固定“最佳”块容量。
- 结构变化时迁移一行：复制共有组件、初始化新增组件、回收移除组件，修正原块 swap-remove 后被搬移实体的位置。完成这些步骤后再公开新位置和查询通知。
- 空标签、共享值、大组件、低占用块和世界销毁策略。首版可先排除共享组件和大对象内联，保留明确扩展点。
- 查询缓存匹配的 Archetype 集合，组件组合出现/消失时更新；稳定扫描不再为每个实体检查所有组件。

保持句柄、命令和查询的外部语义，用一个后端选项做受控 A/B 测试。迁移期间同一组件不能同时由两个后端作为权威数据源；切换应在安全边界执行显式导出/导入，并验证实体及组件值一致。

## 7. 迁移步骤与验收门槛

| 里程碑 | 最小交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：固定第 1～4 项结果 | 核心回归、结构变更语义、精确通知、改进后基准 | 正确性通过；基准包含耗时、分配、环境和原始样本。 |
| M1：句柄与世界边界 | 实体槽位表、代际验证、默认世界兼容门面 | 跨世界、复用、异步旧请求、销毁和溢出案例通过，不改变未迁移系统的行为。 |
| M2：单线程 Sparse Set 试点 | 2～3 个真实数值组件、一个业务系统、ref 查询和命令提交 | 与现有实现/简单参考模型的结果一致；预热后热查询与无扩容增删不产生临时托管分配。 |
| M3：兼容桥接与目标平台验证 | GameObject 桥接、迁移文档、Unity Player 基准 | Mono/IL2CPP 的目标平台正确性和实际帧/内存预算满足要求；决定是否保留托管数组或增加原生后端。 |
| M4：原生存储与读写调度 | 显式依赖、Burst/Jobs、安全释放 | 串行与并行结果一致；竞争检查和退出路径通过；调度收益覆盖任务和同步成本。 |
| M5：可选 Chunk 后端 | 一个固定组合工作负载的 A/B 原型 | 超出样本噪声的稳定收益，且迁移、低占用率和内存成本符合预算；否则不替换 Sparse Set。 |

M2 的测试必须覆盖：随机增删/查询与参考模型比对（记录种子）、首/中/末行 swap-remove、组件列对应关系、空池、容量增长、代际复用、外来世界句柄、失效 ref、批量命令冲突和异常后状态。M4 还需要任务冲突、依赖完成、取消/退出、原生容器泄漏和确定性要求的专项测试。

性能对照从第 1～4 项改进后的实现开始，保持相同实体、组件值、系统工作量和校验结果。至少覆盖 1 万、3 万、10 万实体，冷启动/预热、固定组合/频繁变更、稀疏匹配、多组件查询和不同组件大小。报告中位数、样本范围、分配、保留内存以及真实帧耗时分位数；创建阶段和稳定更新阶段分别计时。

工程验收目标为查询热路径 0 B/帧、增删平均复杂度随操作数近似线性、迁移后的代表性系统不出现明显性能回退。允许的帧预算和内存预算需以项目目标平台确定；这些是待验证的目标，不是已经测得的收益，也不预先承诺倍数提升。针对实际平台完成 M2/M3 后，再决定是否推进 M4/M5。
